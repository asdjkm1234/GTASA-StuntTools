**Status: 🔒 CLOSED 2026-08-12** — phases 0–5 DONE 2026-07-21, phase 6 (documentation) DONE 2026-07-21, and
the close-out taken 2026-08-12: lint clean, coverage floors held (4 108 tests, 91.92 / 82.6 / 92.09 / 92 vs

Renamed + widened twice (was `079-viewers-lab-on-pmb-output`, then `…canonical-build-source`). Depends on
[opensa-pack 003](../../../tools/opensa-pack/docs/plans/003-game-shaped-output.md) — this plan consumes the
game-shaped output that one produces.

The goal in one line: **there is ONE canonical build, and every non-app surface — the lab, the bench
harness, the object-viewer — reads it, so what one shows is what the others show, by construction.** The
main app stays the user's own choice (a picked folder or HTTP); the dev tools do not get to disagree.

This began as "viewers and the lab consume a pmb output". It grew: the 2026-07-20 pak-source bug proved that
_multiple, drifting data sources_ is not tidiness — it is the thing that produced hours of correct-but-useless
measurements. So the plan is now about collapsing every dev surface onto **one build dir, served one way**.

## The two canonical folders (fixed 2026-07-21, user decision)

| Role                      | Path                      | Format                                       | Who reads it                                                |
| ------------------------- | ------------------------- | -------------------------------------------- | ----------------------------------------------------------- |
| **AFTER** / the dev world | `./build/original/opensa`  | own-engine (`.osm`/`.ostex` + `opensa/` pak) | lab, bench-harness, in-game map viewer, object-viewer AFTER |
| **BEFORE** / stock        | `./game-src/original` | RenderWare (`.dff`/`.txd` in `gta3.img`)     | object-viewer BEFORE side                                   |

`./build/original` is the perfect-map-builder `--out` default (see below). It is **git-ignored and local** —
regenerated by each reconvert — so "one version" means "your last build". The `buildTime` stamp (below) is
what makes that version visible across every surface, so two surfaces reading different builds is a thing you
can _see_, not a thing that silently rots.

## What is already DONE (2026-07-21)

- **`--out` is optional, default `./build/original`** (`tools/perfect-map-builder/src/cli.ts`). `--game` /
  `--in` stay required. So a reconvert is just
  `NODE_OPTIONS=--max-old-space-size=12288 npx tsx tools/perfect-map-builder/src/cli.ts --game ./game-src/original --in ./mods-src`.
- **The loading MODE selects the world** (the pak-source fix, foundation for phase 1) →
  [[pak-source-public-shadow-bug]]. `InstallSource.openLoose(path)`, `AssetLoader.openWorld(name)` (local
  loader reads `opensa/<name>` from the picked folder), a Blob branch in `pak-worker` (`blob.slice()` off
  disk — the 073 "pak bytes never touch main" rule holds), `setupStreaming`/`installWater` take
  `PakSource = LocalPakSource | string`, and `use-asset-boot` exposes `pakSource` threaded to the host. No
  `opensa/manifest.json` in the picked folder → throws loudly, never falls back to `public`.
- **`buildTime` in the opensa manifest** — opensa-pack stamps `HH:mm DD-MM-YYYY` at pack time
  (`OspakManifest.buildTime`, `tools/opensa-pack/src/pack.ts`); surfaced on `StreamSetup.buildTime` and shown
  as a grey `build …` line under the F2 debugger title. This is the cross-surface version guard.

## Where the data comes from today (the mess this closes)

| Surface          | How it gets data                                                                                              |
| ---------------- | ------------------------------------------------------------------------------------------------------------- |
| Main app (host)  | user's real game dir via `showDirectoryPicker` → local loader → VFS + world from `opensa/` (post-fix)         |
| Engine lab       | pak only, from `/pak` (or `?src=`), no VFS at all — ad-hoc `fetch` for loose files                            |
| Bench harness    | serves a game dir over HTTP (`game-server.js`: `/__index` + ranged `/f/`) and **fakes** `showDirectoryPicker` |
| Viewers (object) | a compare server on `localhost:3002` (`--before`/`--after` game dirs, RAW `.dff`/`.txd`), or e2e fixtures     |

Four paths, no two agree. The harness's fake picker is the specific hack that shadowed the pak-source bug —
it replaces the real load path with a surrogate, so a test can pass while the real path is broken.

## Design

### The single data contract

A perfect-map-builder output (`./build/original`, a game dir with our format inside the IMGs and world
products under `opensa/`) — **served statically in place, with range support** — mounted the same way by
every dev surface:

```
./build/original  (game dir, pmb --out default)
        │  served statically (range-capable), NOT copied into public/
        │
        ├── opensa/  ──►  world pak (manifest.json + world.ospak + water.bin), streamed
        └── VFS      ──►  resolution: <name>.osm/.ostex → <name>.dff/.txd → warn once
                              ├── engine host (apps/web, via ?loader=http-dir)
                              ├── engine lab
                              └── bench harness (real load path, no fake picker)
```

### Serve in place — do NOT copy the pak into `public/`

The earlier draft said "converted output goes into `./public`". **Superseded 2026-07-21**: `./build/original`
is git-ignored and ~1.4 GB — a Vite `public/` copies it on build. Serve it where it is. Mechanics: extend
`scripts/serve-static.ts` with a `/build → build/` mount (it already maps `/viewer → fixtures/viewer`), or reuse
the harness's ranged server. Small committed test paks may still live in `apps/engine-lab/public/`.

### The missing primitive: an `http-dir` loader mode

The engine already loads the world pak over HTTP (`setupStreaming(engine, urlBase)`), and (post-fix) from a
picked folder Blob. What is missing for "run the FULL game against a served build dir" is a **fetch-backed
`InstallSource`** — the same interface `browserInstallSource(dirHandle)` implements, but reading over HTTP: a
`urlRangeSource(url)` twin of `fileHandleSource` (`.img` via Range, loose files via GET). Add
`AssetLoaderKind = 'http-dir'`; `apps/web` accepts `?loader=http-dir&src=<url>` and runs the full game against
the served dir. This is the generalization of the harness's `game-server.js` + fake picker — with it, **the
harness stops faking the picker and exercises the real load path**. `pakSource` (already landed) extends
naturally: http-dir uses the string `PakSource` (`<base>/opensa`) for the pak and the fetch InstallSource for
the VFS.

### The object-viewer: BEFORE `original` ↔ AFTER `build/original/opensa`

The compare server (`tools/map-optimizer/src/compare-serve.ts --before <dir> --after <dir>`) already takes
two game dirs. Fixing the canonical pair means BEFORE = `./game-src/original`, AFTER =
`./build/original/opensa`. **But this is a feature, not a config change**, because the two sides are different
formats:

- **BEFORE** is stock RenderWare — the compare server reads `.dff`/`.txd` from `gta3.img` today, unchanged.
- **AFTER** is our own-engine format — opensa-pack _replaced_ `<model>.dff → .osm` and `<txd>.txd → .ostex`
  in the archives. Point the current `--after` at `build/original/opensa` and `/models?side=after` returns an
  **empty list** (it filters on `.endsWith('.dff')`), and `/dff?side=after` finds nothing.

So the real work:

1. **compare-serve** reads `.osm`/`.ostex` on the AFTER side (own-engine), not `.dff`/`.txd`.
2. **object-viewer** renders the AFTER model through the engine's `.osm` rigid path (it already renders
   `.osm` in-game — reuse it), instead of `parseDff`.
3. BEFORE stays `.dff`/`.txd` from `original`.

This turns the object-viewer into a true "did the DFF→OSM conversion preserve the model + textures?"
side-by-side — the object-level analogue of the "diff against prod" method (see
[[vehicle-appearance-plan-084]]).

**Coverage caveat (agreed with user):** opensa-pack emits standalone per-model `.osm` for the **by-name**
classes (peds, vehicles, props, breakables, clutter — they own private dictionaries). **Map objects are
welded into the world pak's cells** against a shared dictionary, so a map building may have no standalone
`.osm` archive entry. The AFTER side can therefore show by-name models cleanly; map-only geometry would need
pulling from the pak's cell bundle. The viewer must say which it could resolve, not pretend.

### What the lab keeps

The lab keeps its own Vite root and port, its scene/hour/weather controls, the `?vmodel`/`?at`/`?orbit`
vehicle bench and the bench/soak output contracts ([engine-lab.md](../../development/engine-lab.md),
[benchmarks.md](../../development/benchmarks.md)) — those must survive intact (the bench legs are the check that
no pixels moved). What it loses is its private data path: it loads peds/vehicles from the VFS, exactly as the
game does. `?src=` becomes a build selector pointing at a game dir (default `./build/original`).

## Non-goals

- Changing what any surface RENDERS. Data-path plan; the lab's bench numbers are the check that pixels did
  not move.
- Merging the viewers or the lab into the main app. Separate roots stay.
- Touching the production boot path for real users (`showDirectoryPicker` over the user's own install). A pmb
  output is simply another directory it can be pointed at.
- The hosted-pak / fetch-from-CDN question (opensa-pack `002-fetch-game-paks`).
